# Фронтенд Calendar Booking Service — архитектура и план реализации

Этот документ фиксирует принятые архитектурные решения и поэтапный план
реализации фронтенда. Обновляется по мере продвижения по этапам.

Источники:

- Контракт API: `../../typespec/*.tsp` → `../../typespec/tsp-output/schema/openapi.yaml`
- Референс UI: `../../ui-prototype/*.png`

## Требования (из ТЗ)

- Фронтенд реализуется как отдельная часть приложения.
- Получает данные и выполняет действия **только через API** по контракту.
- Должен корректно работать с отдельно запущенным бэкендом.

## Архитектурные решения

| Область           | Решение                                                                                                                                      |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Расположение      | `frontend/` в корне монорепо — независимый пакет, не знает о бэкенде кроме API                                                               |
| Стек              | Vite + React + TypeScript (strict), Tailwind CSS, shadcn/ui, React Router, TanStack Query, react-hook-form + zod                             |
| Пакетный менеджер | npm (совпадает с `typespec/package.json`)                                                                                                    |
| Контракт          | источник истины — `typespec/tsp-output/schema/openapi.yaml`; типы генерируются оттуда (`openapi-typescript`), руками не пишутся              |
| Мок бэкенда       | **Prism** (`@stoplight/prism-cli`) поднимает мок-сервер прямо по openapi.yaml — фронтенд разрабатывается и тестируется без реального бэкенда |
| Реальный бэкенд   | адрес задаётся через `VITE_API_BASE_URL` (.env), переключение mock/real — только через переменную окружения, кода не касается                |
| Компоненты UI     | добавляются через `shadcn` CLI (при наличии — через shadcn MCP server) — код компонентов живёт в репо, а не в node_modules                   |
| Линт/формат       | oxlint (линтер) + prettier (форматирование)                                                                                                  |

### Заметки по окружению

- Node.js не был установлен в системе — поставлен локально в
  `~/.local/opt/node` (v22.14.0), добавлен в `PATH` через `~/.bashrc`.
  При работе в другом окружении может понадобиться установить Node.js заново.
  Внимание для неинтерактивных оболочек (CI, скрипты): `~/.bashrc` там не
  читается, `npm`/`node` вне системного `PATH` — нужен явный
  `export PATH="$HOME/.local/opt/node/bin:$PATH"` перед вызовом.
- Баг shadcn CLI: без `paths` в корневом `tsconfig.json` (там были только
  `references` на `tsconfig.app.json`/`tsconfig.node.json`) CLI не резолвил
  алиас `@/*` и писал файлы в буквальную папку `./@/...` в корне проекта.
  Исправлено добавлением `compilerOptions.paths` в корневой `tsconfig.json`
  (алиас также объявлен в `tsconfig.app.json` и `vite.config.ts`).
- Ещё один баг shadcn CLI: в стиле `radix-nova` компонент `form` есть в
  реестре, но его `files` пустой — `npx shadcn add form` завершается без
  ошибки и ничего не создаёт. Добавление из стиля `new-york-v4` тянет за
  собой перезапись `button.tsx`/`label.tsx` чужого стиля, поэтому
  `src/components/ui/form.tsx` перенесён вручную (изменены импорт `Label`
  на локальный алиас и добавлен третий генерик `TTransformedValues`
  у `FormField` — версия из реестра отстала от react-hook-form 7.84).
- `npm audit`: react-router (RSC Mode CSRF Bypass, GHSA-qwww-vcr4-c8h2) —
  не применимо, т.к. используется декларативный клиентский роутинг без RSC.
  Уязвимости в транзитивных зависимостях `@stoplight/prism-cli` — это dev-only
  инструмент для мока API, в продакшн-бандл не попадает.

### Этап 5. Сквозные требования

Этап приводит уже написанные экраны (этапы 2–4) к единому уровню качества.
Ничего нового по функциональности не добавляется — только сквозные свойства:
валидация, тексты, доступность, адаптивность, устойчивость к сбоям.

#### Закрытые решения (перед стартом этапа)

| Вопрос                | Решение                                                                                                                                    |
| --------------------- | ------------------------------------------------------------------------------------------------------------------------------------------ |
| Ограничения моделей   | Добавляем в контракт TypeSpec (источник истины), клиентский zod зеркалит его                                                               |
| Формат `EventType.id` | Строгий kebab-case `^[a-z0-9]+(-[a-z0-9]+)*$` — строже текущего клиентского правила (`[A-Za-z0-9._~-]`), поэтому ужесточение одностороннее |
| `SlotCalendar` и a11y | Вариант 1: переход на `react-day-picker` через `shadcn add calendar`; свой грид с ручным ARIA не пишем                                     |
| Тексты                | Один модуль `src/lib/messages.ts`, форматирование дат остаётся в `src/lib/datetime.ts`                                                     |

#### Порядок работ

Шесть шагов, каждый — отдельный коммит, после каждого прогоняются
`typecheck`, `lint`, `format:check`, `build`.

| #   | Шаг                                         | Пункт ТЗ | Почему здесь                                                           |
| --- | ------------------------------------------- | -------- | ---------------------------------------------------------------------- |
| 1   | Ограничения в контракте + регенерация типов | 5.1-A    | Меняет генерируемые типы — всё остальное опирается на них              |

#### Шаг 1. Ограничения в контракте (5.1-A) — ✅ выполнено

Исходное состояние: в `typespec/models.tsp` у `EventType`/`EventTypeCreate`
нет ни одного декоратора ограничения — в `openapi.yaml` только `required` и
типы. Зеркалить нечего, поэтому ограничения сначала появляются в контракте.

Коммит затрагивает общий контракт → согласовать с бэкендом, вынести отдельно
от фронтенд-изменений.

Правки:

- `typespec/models.tsp`:
  - общий скаляр, чтобы правило не дублировалось между моделями:
    `@minLength(1) @maxLength(64) @pattern("^[a-z0-9]+(-[a-z0-9]+)*$") scalar EventTypeId extends string;`
    (id попадает в пути `/event-types/{id}`, `/event-types/{id}/slots` и
    в маршрут фронтенда `/book/:eventTypeId`)
  - `EventType.id`, `EventTypeCreate.id`, `Booking.eventTypeId`,
    `BookingCreate.eventTypeId` → `EventTypeId`
  - `name`: `@minLength(1) @maxLength(100)`
  - `description`: `@minLength(1) @maxLength(500)`
  - `durationMinutes`: `@minValue(5) @maxValue(480)`
- `typespec/event-types.tsp`: `read(@path id: EventTypeId)`
- `typespec/slots.tsp`: `list(@path eventTypeId: EventTypeId)`
- регенерация: `npx tsp compile .` в `typespec/`, затем
  `npm run generate:api` во `frontend/`

Что проверить:

- `frontend/src/api/schema.d.ts` пересобран; ожидаемое изменение — появление
  именованной схемы `EventTypeId` и ссылок на неё. **Ограничения в типы не
  попадают** (`openapi-typescript` их не кодирует) — это ожидаемо, см. шаг 3
- `npm run mock:api` поднимается на обновлённом `openapi.yaml`
- `POST /event-types` с телом `{"id":"Bad_Id",...}` → Prism отвечает 422
  (валидация тела запроса по схеме). Это и будет инструментом проверки
  «зеркальности» на шаге 3

Риски:

- `typespec/tsp-output/` в `.gitignore` — в коммит попадают только
  `*.tsp` и сгенерированный `frontend/src/api/schema.d.ts`. Любому, кто
  поднимает мок, нужен локальный `tsp compile`
- ужесточение `id` до kebab-case: существующие данные бэкенда/примеров с
  другими id станут невалидными — пункт для согласования

Результат проверки на Prism-моке (`POST /event-types`):

| Тело запроса                        | Ответ                 |
| ----------------------------------- | --------------------- |
| `id: "consultation-30"` (валидное)  | 201                   |
| `id: "Bad_Id"` (не kebab-case)      | 422                   |
| `id` 64 символа / 65 символов       | 201 / 422             |
| `name: ""` / 100 символов / 101     | 422 / 201 / 422       |
| `description` 501 символ            | 422                   |
| `durationMinutes` 3 / 5 / 480 / 600 | 422 / 201 / 201 / 422 |

В `schema.d.ts` появилась схема `EventTypeId` (алиас `string`) и ссылки на
неё в `EventType`, `EventTypeCreate`, `Booking`, `BookingCreate` и параметрах
путей. Ограничения в типы, как и ожидалось, не попали.
`typecheck`, `lint`, `format:check`, `build` — чисто.

### Этап 6. Тесты

Задача этапа — превратить ручные проверки этапов 1–5 в автоматические.
Каждый критерий готовности предыдущих этапов проверялся человеком или
одноразовым скриптом вне репозитория; здесь эти проверки переезжают в код и

Этап выполняется **после этапа 5** и опирается на его результаты:

#### Шаг 2. MSW: фикстуры, handlers, защита от расхождения с контрактом

Зависимость (dev): `msw`.

Структура `src/test/`:

- `fixtures.ts` — типизированные данные (`EventType[]`, слоты, брони). Типы
  импортируются из `@/api/*`, поэтому расхождение с контрактом ломает
  `typecheck`. Важные свойства фикстур:
  - слоты минимум на три разных дня, из них хотя бы один — в следующем месяце
    (иначе навигация по месяцам в календаре непроверяема)
  - даты генерируются относительно «сегодня», а не захардкожены, иначе тесты
    протухнут; для детерминизма время фиксируется (`vi.setSystemTime` в
    unit-тестах, `page.clock.setFixedTime` в E2E)
  - список встреч намеренно **не отсортирован** по `start` — на нём
    проверяется клиентская сортировка `UpcomingBookingsTab`
- `state.ts` — минимальное состояние в памяти (созданные типы событий,
  занятые слоты) + `resetState()` в `beforeEach`. Без него не воспроизвести
  ни 409, ни «созданный тип сразу виден в списке»
- `handlers.ts` — все пять операций контракта:
  - `GET /event-types` — список из состояния
  - `GET /event-types/{id}` — 200 либо 404 с телом `Error`
  - `POST /event-types` — 201; 409 при дубликате `id`
  - `GET /event-types/{id}/slots` — слоты за вычетом занятых
  - `POST /bookings` — 201; 409 `slot_already_booked` на занятый слот;
    400 `slot_not_available` на слот вне окна 14 дней
- `server.ts` (`setupServer`) для Node и `browser.ts` (`setupWorker`) для E2E;
  `npx msw init public/` кладёт `public/mockServiceWorker.js`
- handlers регистрируются на абсолютный URL из `VITE_API_BASE_URL`; в
  конфиге Vitest он задаётся явно (`env`), иначе пути не совпадут
- `onUnhandledRequest: 'error'` — незамоканный запрос валит тест, а не уходит
  в реальную сеть

**Контрактная проверка фикстур** — `src/test/contract.test.ts`:
читаем `../typespec/tsp-output/schema/openapi.yaml` (`js-yaml`), валидируем
ответы каждого handler'а по `components.schemas` через `ajv` +
`ajv-formats` (`$ref` резолвятся добавлением всего документа в Ajv). Именно
эта проверка не даёт нашему моку разойтись с контрактом и оправдывает отказ
от Prism в тестах. Побочный эффект: `openapi.yaml` лежит в
`typespec/tsp-output/`, который в `.gitignore` → тест пропускается с
внятным сообщением, если файла нет, а в CI он генерируется явным шагом.

Почему не `openapi-msw`: он даёт типобезопасность путей, но не проверяет
ограничения (`pattern`, `minLength`) — их ловит только Ajv. Можно добавить
позже, ценность невелика.

#### Шаг 5. Playwright E2E

Зависимость (dev): `@playwright/test`; в CI — `npx playwright install
--with-deps chromium`.

`playwright.config.ts`: `testDir: 'e2e'`, `webServer` поднимает

`desktop` (chromium 1280×720), `mobile` (Pixel 5), `smoke` (против Prism).

Включение MSW в браузере: в `src/main.tsx` — условный динамический импорт

отдельный чанк; в обычной прод-сборке (`--mode production`) флаг ложный,

неприемлемо — исключить модуль из прод-сборки через `rollupOptions.external`
для соответствующего mode.

Сценарии:

1. **Гостевой happy path** — `/` → «Записаться» → тип события → день →
   время → «Подтвердить» → карточка «Встреча забронирована»; после возврата
   слот исчез из списка
2. **Конфликт** — сервер отвечает 409: показано сообщение, выбор сброшен,
   слоты перезапрошены
3. **Админский сквозной** — создать тип события → он в таблице админки →
   он же на `/book` → забронировать его слот → встреча во вкладке
   «Предстоящие встречи» с типом, датой, временем и длительностью
   (автоматизация критерия готовности этапа 4)
4. **Валидация формы** — пустой сабмит: ошибки показаны, запроса нет
5. **Сетевой сбой** — `page.route(..., route => route.abort())` → экран
   ошибки с «Повторить»; после снятия перехвата повтор восстанавливает
   данные без перезагрузки (автоматизация критерия этапа 5.5)
6. **Доступность** — `@axe-core/playwright` на `/`, `/book`, `/book/:id`,
   `/admin`: ноль нарушений уровня `serious`/`critical`
7. **Клавиатура** — гостевой сценарий целиком на Tab/стрелках/Enter, без
   мыши (автоматизация критерия этапа 5.3)
8. **Адаптив** — в проекте `mobile` на четырёх маршрутах проверяем
   `document.documentElement.scrollWidth <= clientWidth` (автоматизация
   критерия этапа 5.4)
9. **Prism smoke** (`e2e/smoke.spec.ts`, проект `smoke`, без MSW) — против
   `npm run mock:api`: приложение поднимается и рисует список типов событий
   на данных из контракта. Ловит расхождение нашего мока с реальным
   `openapi.yaml` на уровне работающего приложения

Детерминизм: `page.clock.setFixedTime` фиксирует «сегодня», дни и слоты
выбираются по доступной имени из фикстуры, а не по номеру ячейки — иначе
тест сломается при смене месяца или дня недели.

#### Шаг 6. CI

Реализовано: `.github/workflows/frontend.yml` (существующий `hexlet-check.yml`

Один job `frontend` (ubuntu-latest, `defaults.run.working-directory: frontend`):

1. `actions/setup-node@v4` — Node 22
2. **Генерация контракта:** `npm ci && npx tsp compile .` в `typespec/`

3. `npm ci` (frontend)
4. `npm run typecheck`, `npm run lint`, `npm run format:check`

Смоук и E2E используют собственные `webServer` из `playwright*.config.ts`,

### Этап 8. Docker и деплой на Railway — ✅ выполнено

Деплой выведен в отдельный план (`plan260815.md`): один контейнер «SPA + API»
на одном порту, деплой на Railway.

**Решение:** многоступенчатый `Dockerfile` в корне репозитория — stage 1
(`node:22`) собирает фронтенд с `VITE_API_BASE_URL=/` → same-origin
(`apiBaseUrl === ""`, `isApiConfigured === true`, относительные запросы на
тот же origin); stage 2 (`eclipse-temurin:25-jdk`) копирует `frontend/dist/*`
в `backend/src/main/resources/static/` и собирает `bootJar`; stage 3
(`eclipse-temurin:25-jre`) запускает `booking-0.0.1-SNAPSHOT.jar`, слушающий
`PORT` от платформы. `.dockerignore` исключает `node_modules`, `build`,
`.gradle`, `dist*`, `coverage`, `plan*.md`, `.env`. Обязателен `.npmrc`
(`legacy-peer-deps=true`) в stage 1 — без него `npm ci` падает на peer-конфликте
(`@hookform/resolvers` vs `ajv-formats`).

**SPA-fallback:** `SpaForwardController` (forward `/index.html` для
`/book`, `/book/**`, `/admin`) + MockMvc-тест `SpaForwardTest`; API-маппинги
не затрагиваются (404-тесты остаются зелёными).

**Same-origin фиксация:** тесты в `src/api/client.test.ts`
(`VITE_API_BASE_URL=/` → `apiBaseUrl === ""`, `isApiConfigured === true`, нет
короткого замыкания `notConfigured`).

**Публичный URL:** <https://pleasant-art-production-18a0.up.railway.app> —
проверены `/` (HTML 200), `/book` (SPA-fallback), `/event-types` (JSON),
happy-path брони через API.

**Риски:** H2 in-memory (данные слетают при рестарте — для демо ок);
локальный docker-демон недоступен, образ собирает Railway.
