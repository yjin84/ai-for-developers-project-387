# Roadmap: улучшения backend

Предложения по итогам аудита `backend/` (Spring Boot 4.1, JDK 25, H2).
Все изменения должны сохранять контракт `typespec/` и зелёные `./gradlew build`.

## 1. GET /bookings: N+1 и неограниченная загрузка в память

**Проблема.** `BookingService.listAll()` (`backend/.../service/BookingService.java:71`)
вызывает `bookingRepository.findAll()` без пагинации и без `join fetch`.
`BookingEntity.eventType` помечен `FetchType.LAZY`, поэтому каждый
`booking.getEventType()` порождает отдельный SELECT (N+1). С ростом числа броней
`GET /bookings` грузит всю таблицу в память и генерирует N+1 запросов.

**Решение.**
- В `BookingRepository` добавить JPQL с `join fetch b.eventType` и сортировкой по
  `start` (сортировка на сервере избавит от клиентской в `src/lib/…`, см. §«Admin
  flows» в AGENTS.md).
- Ограничить выдачу пагинацией (`Pageable` + `Page<…>`). Если контракт не
  разрешает пагинацию в ответе — ввести защитный лимит снаружи (например,
  `spring.data.web.pageable.max-page-size`), не трогая форму ответа.

**Эффект.** Устраняет N+1, контролирует память при росте данных.

## 2. POST /bookings принимает старты вне сетки слотов

**Проблема.** `BookingService.create()` проверяет только окно
`[now, now + daysAhead)` (`BookingService.java:47-52`), но не сверяет `start` с
правилами генерации сетки из `SlotScheduleService.freeSlotsFor()`
(`SlotScheduleService.java:43-78`): рабочий день, часы `start..end`, шаг `stepMin`.
Клиент может забронировать старт, который фронтенд никогда не покажет
(суббота, 13:30 при шаге 60 и т.п.), — бронь «повисает», занимая уникальный `start`.

**Решение.** Ввести общий валидатор «старт легитимен для сетки», используемый и при
генерации слотов, и при создании брони: рабочий день + `start >= startHour`,
`start + duration <= endHour + step` и `start` кратен `stepMin` от начала дня
(в зоне `SLOT_TIMEZONE`). При несоответствии — 400 `slot_not_available`.
Логику вынести из `SlotScheduleService` в отдельный метод/класс, чтобы оба
сервиса пользовались одной правдой (единственный источник — `SlotProperties`).

**Эффект.** Backend и фронтенд согласованы: бронь возможно создать только на
реально существующий слот; исчезают «теневые» брони.

## 3. Схема БД через миграции вместо `ddl-auto=create-drop`

**Проблема.** `application.properties:4` использует
`spring.jpa.hibernate.ddl-auto=create-drop`. С файловой БД
(`DB_URL=jdbc:h2:file:...`) схема пересоздаётся при каждом рестарте, данные
нестабильны; менять схему вручную нельзя — она выводится из сущностей.

**Решение.**
- Подключить Flyway (`org.flywaydb:flyway-database-h2`), перенести схему
  (`event_types`, `bookings`, уникальный индекс на `bookings.start`) в
  `V1__init.sql`.
- В prod-профиле выставить `spring.jpa.hibernate.ddl-auto=none` (или `validate`),
  оставив `create-drop` только для локального dev-профиля и тестов.
- Учитывать в `typespec/` и `schema.d.ts` любые будущие изменения модели
  (процесс из AGENTS.md §«Contract-driven API»).

**Эффект.** Предсказуемая схема, безопасная эволюция БД, пригодность
`jdbc:h2:file` для персистентных данных.

# Frontend

## 4. Выбранный слот не сверяется со свежим списком слотов

**Проблема.** В `BookSlotPage.tsx:48` `selectedSlot` — обычный `useState`,
он не обновляется при приходе нового списка слотов. После инвалидации
(`queryClient.invalidateQueries` при 409, `BookSlotPage.tsx:76`) или рефетча по
фокусу окна выбранный слот может исчезнуть из `slotsByDay`, но «Подтвердить»
останется активным (`SlotTimeList.tsx:117`): пользователь подтверждает слот,
которого больше нет, и получает повторный 409 `slot_already_booked`.

**Решение.** Держать в состоянии только идентификатор слота
(`selectedSlotStart`), а сам объект слота выводить из свежих данных —
`slotsByDay.get(selectedDay)?.find(s => s.start === selectedSlotStart)`. Если
слота больше нет в списке, выбор очищается автоматически и кнопка блокируется;
дополнительно при изменении `slotsQuery.data` очищать выбор, если день потерял
все слоты. Существующий обработчик 409 оставить как страховку на гонку.

**Эффект.** Исчезает «мёртвое» подтверждение и повторные 409; UI сам
дезактивирует недоступный выбор.

## 5. QueryClient не повторяет запросы на 5xx

**Проблема.** `queryClient.ts:19-22` возвращает `false` для любого `ApiError`,
включая 500-е. Ошибки сервера (рестарт бэкенда, H2, разворачивание) часто
транзиентны и самоустраняются, в отличие от 4xx — повтор здесь был бы полезен.
Сейчас пользователь видит «Ошибка сервера» после первого же сбоя.

**Решение.** В `retry` различать статусы: не повторять только 4xx и
нормализованные бизнес-ошибки (`slot_*`), а на `error.status >= 500` делать
1-2 повтора с задержкой по умолчанию (как для `NetworkError`). Изменение
ограничено `src/api/queryClient.ts`, поведение покрыть в тесте API-слоя.

**Эффект.** Самовосстановление после транзиентных сбоев без изменения кода
экранов.

## 6. Нет возможности отменить бронь (у админа)

**Проблема.** Контракт содержит только создание и список броней (5 операций) —
у админа нет способа отменить ошибочно созданную встречу; слот остаётся занят
до конца окна записи.

**Решение.** Расширить контракт: `DELETE /bookings/{id}` → `204` (успех) /
`404` (нет такой брони), затем backend-метод и кнопка «Отменить» в
`UpcomingBookingsTab` с подтверждением в диалоге. Следовать процессу
AGENTS.md §«Contract-driven API»: `typespec/*.tsp` → `generate:api` →
`schema.d.ts` → backend (контроллер + сервис + `ApiExceptionHandler`) →
фронтенд. Инвалидировать `queryKeys.bookings.upcoming()` и слоты
затронутого типа события после отмены.

**Эффект.** Замкнутый цикл управления бронями; занятые слоты освобождаются.

### Кандидаты, не вошедшие в топ (frontend)

- Запрос слотов на `/book/:id` можно не запускать, пока не получен сам тип
  события (`eventTypeQuery.isSuccess`) — сейчас оба запроса летят параллельно и
  при 404 типа события лишний раз стреляет `/slots`.
- Дата-утлиты опираются на строковые даты (`new Date(\`${day}T00:00:00\`)` в
  `BookSlotPage.tsx:57,109`, `SlotCalendar.tsx:37`). Свести восстановление `Date`
  из ключа дня в одну функцию в `src/lib/datetime.ts`, чтобы исключить расхождение
  между группировкой и рендером.
